Survsys.Data gains a lean treatment catalogue (Treatment: a named treatment with its active and default-treatment flags), condition-specific treatment lists (ConditionTreatment: the treatments a condition offers, as a join), a vaccine catalogue seeded via HasData from the legacy CDC vaccine codes (Vaccine: code and description), and per-case vaccine records (PersonVaccine: a vaccine administered to a case, with its dose number, administered and expiration dates, lot number and comment), each with its IEntityTypeConfiguration, all in one migration. Treatment vaccine entities

Add the treatment and vaccine domain to Survsys.Data as entities and their IEntityTypeConfiguration files, and nothing of the migration yet. Treatment is the catalogue under the legacy treatment table kept lean: id, name (required, the legacy treatment_name, as a list shows it), active (bool, default true), default_treatment (bool, default false), created_at. ConditionTreatment is the condition-specific list under the legacy condition_treatment table: condition_id and treatment_id as a composite key and nothing else (follow PersonConditionLab for the keyed-join shape with no identity column and no navigation), with a FK to conditions (no cascade) and a FK to treatments (cascade on delete, so removing a treatment removes its links). Vaccine is the catalogue under the legacy vaccine table: id, code (required, unique), description (nullable), sort_order (int); seed it via HasData in VaccineConfiguration from the legacy CDC vaccine rows in V0169__create_vaccine_tables.sql (code, description, sort_order), the way AgencyConfiguration and CoreElementConfiguration seed reference rows. PersonVaccine is the per-case record under the legacy person_vaccine table kept lean: id, person_condition_id (FK to person_conditions, cascade on delete -- a record belongs to its case), vaccine_id (FK to vaccines, no cascade -- the catalogue is protected), administered_date (nullable date), dose_number (nullable int), lot_number (nullable), expiration_date (nullable date), comment (nullable), created_at. Register Treatment, ConditionTreatment, Vaccine and PersonVaccine as DbSets on SurvsysDbContext. Follow Condition/ConditionConfiguration and PersonConditionLab/PersonConditionLabConfiguration for the entity-plus-configuration shape, the legacy column names and the XML-doc grounding in the legacy table and its source file; configurations stay internal sealed.

Treatments api

Add the /api/treatments slice to Survsys.Api, following OutbreakEndpoints: a static TreatmentEndpoints with a public pure WhyNotATreatment validator the unit suite proves (name required and bounded, and no duplicate condition id in the submitted list), a public ToResponse projection, an AddTreatments service registration and a MapTreatments that Program.cs calls beside the others, and an internal sealed TreatmentQueries that is the one holder of the DbContext for the slice (no Survsys.Data type enters an endpoint signature, as the architecture test requires). Endpoints: GET /api/treatments lists treatments (by name) as PagedResult<TreatmentResponse> carrying the treatment's name, active and default-treatment flags and the count of conditions it is listed for; GET /api/treatments/{id} returns TreatmentDetailResponse carrying the treatment and the id and name of each condition it is listed for, refusing an unknown id as a 404; POST and PUT create and save a treatment together with its whole condition-link set in one call from SaveTreatmentRequest, refusing WhyNotATreatment as a 400, an unknown id as a 404 and a condition id that does not exist as a 400; GET /api/conditions/{conditionId}/treatments lists the treatments a condition is listed for as PagedResult<TreatmentResponse> (the condition-specific list), refusing an unknown condition as a 404. Add the contracts as records in Survsys.Contracts.
