Audit interceptor

Add AuditInterceptor to Survsys.Data and wire it into SurvsysDbContext. AuditInterceptor is a SaveChangesInterceptor (overriding both SavingChanges and SavingChangesAsync) that, given the saving context, snapshots the ChangeTracker.Entries() whose State is Added, Modified or Deleted into a list first -- skipping any entry whose entity is an AuditEntry, so the audit never audits itself -- then for each snapshotted entry adds one AuditEntry to that same context carrying the entry's table name (entry.Metadata.GetTableName()), its primary key rendered from the key properties' current values (entry.Metadata.FindPrimaryKey()), the operation mapped from the state (Added->Insert, Modified->Update, Deleted->Delete) and DateTime.UtcNow, before returning the base result; snapshot before adding so the newly added AuditEntry rows are not themselves iterated. Because the AuditEntry rows are added to the saving context, they are written in the same SaveChanges and the same transaction as the change they record -- a rolled-back save takes its audit rows with it. Wire it by overriding SurvsysDbContext.OnConfiguring to call optionsBuilder.AddInterceptors(new AuditInterceptor()), so every context the application and the suite build carries the audit without either call site changing; document in the class XML doc that this stands in for the legacy PostgreSQL row triggers. Change no entity, configuration or migration in this step.

Audit integration tests

Add Survsys.IntegrationTests/AuditInterceptorTests.cs proving the AuditInterceptor against the real SQL Server fixture, following the existing integration tests (SurvsysDbContextTests and TreatmentEndpointsTests) for the SqlServerFixture harness and the NewContext pattern. Use a Treatment as the subject because it has no foreign keys. Assert: inserting a Treatment through a context and saving writes exactly one audit_entries row for the treatments table and that treatment's key with operation Insert; updating that treatment and saving writes an Update row for the same table and key; deleting it and saving writes a Delete row; and, enrolling an insert in an explicit transaction (context.Database.BeginTransaction) that is rolled back rather than committed, no audit row for that treatment's table and key persists when read back through a fresh context. Scope every assertion to the audited table name and the subject's key rather than to a global row count, because the fixture's database is shared across the suite. The suite's own seed data is loaded by raw SQL and so is not audited, which the test may rely on but should not assert. Register nothing and change no other file.
