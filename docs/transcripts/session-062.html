Work Plan

Give every case an event type and make contacts cases of their own. Survsys.Data gains the event type vocabulary -- EventTypes with the codes morbidity, contact and assessment -- and an event_type column on person_conditions, required, defaulting to morbidity so every existing case becomes a morbidity report through the migration; exposure_contacts gains a nullable person_condition_id naming the contact event a contact row opened, in the same migration. Survsys.Api stores and answers the event type: POST /api/person-conditions takes an optional event type of morbidity (the default) or assessment, and PersonConditionResponse carries it. POST /api/exposures/{id}/contact-events adds a contact to an exposure as a contact event of its own -- the person either an existing one found by search (personId) or a new one created from the request -- writing in one save the person where new, the exposure_contacts row and a person_conditions row of type contact with the index case's condition and agency and a record number of its own; POST /api/person-conditions/{id}/promote turns a contact event into a morbidity report in place and queues it for notification, refusing any case that is not a contact event. The batch CSV contact import stops being a dry run: it takes the exposure the batch is under, and every row the parser accepts is saved as a new person and a contact event under that exposure in one save, while each refused row comes back with its line and reason. Survsys.Web shows the event type in the report header, offers Promote to morbidity report on a contact event, lets the new-report screen choose morbidity or assessment, and on the Contacts tab adds a contact to an exposure through the person search panel or a new person, links each contact row to its contact event, and gives an upload panel that imports a CSV under a chosen exposure and lists each refused row and why. Survsys.UnitTests proves the vocabulary, the pure request rules, the row-to-person mapping and the clients; Survsys.IntegrationTests proves against SQL Server a contact event's creation (existing and new person) and promotion, and an import of good and refused rows.

Contact events endpoint

Add a contact as a contact event of its own, and promote one. Survsys.Contracts/CreateContactEventRequest.cs is record CreateContactEventRequest(int? PersonId = null, CreatePersonRequest? NewPerson = null, string? ContactType = null, DateOnly? ExposureStart = null, DateOnly? ExposureEnd = null); ExposureContactResponse gains int? PersonConditionId = null at the end, and Survsys.Api/ExposureEndpoints.cs's contact projection fills it. Survsys.Api/ContactEventEndpoints.cs maps POST /api/exposures/{id}/contact-events: a pure WhyNotAContactEvent(request) refuses, as a 400 Problem Details, a request naming both or neither of PersonId and NewPerson, a non-positive PersonId, and a NewPerson PersonEndpoints.WhyNotAPerson refuses; an exposure id naming no exposure is 404; a PersonId not on file is 400. An internal ContactEventQueries in that file adds, for an exposure and a list of people (each an existing person id or a new Person), in one SaveChanges: each new person, one exposure_contacts row per person (with the request's contact type and dates) whose PersonConditionId is the contact event, and the contact event -- a person_conditions row of event type contact with the exposure's report's condition and agency, created now, onset date, MMWR week and year and initial workflow state set as PersonConditionQueries.Add sets them, and a record number of its own, issued in sequence after the year's highest by RecordNumber.SequenceIn and RecordNumber.For so a batch takes consecutive numbers; it is not queued for notification and gets no auto-assigned forms. The endpoint answers 201 with the ExposureContactResponse. Register it in Survsys.Api/Program.cs beside the exposures. In Survsys.Api/PersonConditionEndpoints.cs map POST /api/person-conditions/{id}/promote: 404 for no such report, a 400 Problem Details from a pure WhyNotAPromotion(eventType) for a case that is not a contact event, otherwise the event type becomes morbidity, the case is queued for notification as a new report is, and it answers 200 with the PersonConditionResponse. Both routes are POSTs under /api, which PrivilegeRules already gates on edit_cases. Survsys.UnitTests/ContactEventEndpointsTests.cs proves WhyNotAContactEvent, and Survsys.UnitTests/PersonConditionEndpointsTests.cs gains WhyNotAPromotion. Non-goals:

  • No person matching on import or on add: an imported row always creates a new person, and finding duplicates and merging them is phase 9 (sessions 68-70).
  • No contact_import_batch, contact_import_row or contact_import_answer tables: the import's answer is not kept as a batch history, and no import is re-run or undone.
  • No filtering of contact or assessment events out of, or event-type filter on, the case search, the Events screen, the work queues, the reports, or the CDC, NMI and IBIS exports; a contact event is simply not queued for notification until it is promoted.
  • No reference tables or pick lists for event type, contact type or contact disposition (session 64): contact type stays a free-text code, and the existing exposure entry form keeps its typed person id boxes.
  • No legacy parent_id on person_conditions and no demotion: a contact event is tied to its index case only through its exposure_contacts row, and promotion changes the event's type in place rather than creating a second case.
  • No walkthrough, user guide, technical guide or planning document edits (session 66 writes the phase's walkthroughs): every existing identifier and visible text the walkthroughs name is kept, including the header's Morbidity label for a morbidity report, and new controls take identifiers of their own.
  • No release packaging or publishing and no packaging block in dabbler.yaml.
