Work Plan

Give Survsys users, roles and privileges, put every API endpoint behind them, and record who opened which case. The privileges are a fixed catalogue the code checks, named once in Survsys.Contracts.Privileges because both tiers read them: view_cases, edit_cases, manage_reference_data and manage_users. Survsys.Data gains users (user name, display name, password hash, active), roles (name), user_roles, role_privileges (role and privilege name) and access_records (user, case morbidity report, when), in one UsersAndRoles migration that seeds an Administrator role holding every privilege. Survsys.Api authenticates with ASP.NET Core's own bearer tokens: POST /api/sign-in (anonymous) checks the password with the framework's PasswordHasher and issues a token whose claims are the user's id, name and the privileges of their roles; GET /api/me answers who the caller is. One fallback authorisation policy covers every endpoint already mapped and every one mapped later: the caller must be signed in, and PrivilegeRules, a pure rule over the request's method and path, names the privilege the request needs (reference data and core elements are readable by any signed-in user and written with manage_reference_data; users, roles and the access audit need manage_users; every other API read needs view_cases and every other write edit_cases); an anonymous caller is answered 401 and an unprivileged one 403, as Problem Details. At startup the API ensures the administrator Survsys:Administrator:UserName and :Password name exists when both are configured, so a fresh database has someone who can sign in, and no credential lives in a file. UserEndpoints and RoleEndpoints list, create and update users (roles, active flag, a new password) and roles (their privileges), and GET /api/privileges lists the catalogue. Opening a case morbidity report writes an access record, and GET /api/access-audit pages them newest first, optionally for one report. Survsys.Web signs a person in with a statically rendered sign-in page that posts to the tier, keeps the API token and the privileges in its authentication cookie, sends the token on every API call through one delegating handler, requires a signed-in user for every screen, offers sign-out, shows each navigation entry only to a user holding the privilege its screen needs, and gains the user and role administration screens. The integration suite signs its client in as the configured administrator and proves an anonymous and an unprivileged caller are refused; the end-to-end harness starts the API with an administrator and signs the browser in before each walkthrough, and each walkthrough's Before you start says the reader signs in first.

Non-goals:

  • No agency- or jurisdiction-scoped roles (the legacy user_agency_role), no condition-level permissions (user_condition) and no sealed-record access (user_broken_seal): a role's privileges apply everywhere.
  • No privilege editor and no privilege table: the four privileges are a catalogue in code, because only code can enforce one; a role chooses among them.
  • No password history, expiry, complexity policy, lockout, password reset by email, refresh tokens or external identity provider: a token lives for the sign-in and a role change takes effect at the user's next sign-in.
  • No field masking or record-level filtering of what a privileged caller is served: authorisation decides whether a request is answered, never what is left out of the answer.
  • No access audit screen: the access record is written and readable from GET /api/access-audit; only a report being opened is recorded, not every read of every resource.
  • No change to any endpoint's route, request or response shape, and no saved views, exports or new walkthroughs: those are sessions 33 and 34.
