Session 107: The integration suite before every release, on SQL Server in a container

*Inserted after session 106. The framework's run of record is the unit suite alone, and it has never run the integration suite. Sessions whose plans say "the integration suite included" still recorded a unit-only run. So an integration failure goes unseen until someone runs the suite by hand: session 95 found PersonMergeEndpointsTests.AMergeThatFailsPartwayLeavesBothPeopleUnchanged broken since session 94. The suite needs a reachable SQL Server, so it should bring its own. Testcontainers for .NET (Testcontainers.MsSql) is the usual way to do that: the fixture starts a SQL Server 2022 container, waits until it is ready, and hands back its connection string. dotnet test then needs nothing started first. Nothing in the schema uses a Windows-only feature. This comes before release 0.14.0 so that release is the first one the integration suite gates.*

*Non-goals: ordinary sessions keep the unit suite as their run of record, and no CI pipeline runs the integration suite. No script, no compose file, and no password anyone has to keep: Testcontainers generates one for each run. The end-to-end harness keeps its own server for now. No product code changes. If the first run in a container fails because of the product rather than the container, the failure is recorded in the session's notes and a repair session is planned before the release.*

  1. Register.
  2. Survsys.IntegrationTests: a reference to Testcontainers.MsSql, and SqlServerFixture starting a SQL Server 2022 container for the run when SURVSYS_SQLSERVER is not set. When it is set, the fixture uses that server as it does today, so the suite can still run against a local SQL Server. The container is removed when the run ends. If no container engine is reachable, the fixture fails loudly, naming the engine it tried, DOCKER_HOST and SURVSYS_SQLSERVER, the same way an unreachable server fails it today. It never skips.
  3. Podman on the operator's machine: Testcontainers reaches Podman through its Docker-compatible API, with DOCKER_HOST pointing at it where Docker Desktop would otherwise answer. Whether Testcontainers' cleanup container (Ryuk) has to be turned off with TESTCONTAINERS_RYUK_DISABLED is settled by trying it. The session's notes record the settings that worked, and none of them is written to a file the repository tracks.
  4. dabbler.yaml: the integration suite becomes one a release session must run whole and green, while an ordinary session's run of record stays the unit suite. The session first finds out what the installed router can express: a suite only a release runs, or one the release selects. Its notes say which was used. If the router can express neither, the release gate becomes a documented step of the release session, and the notes say so.
  5. docs/technical/README.md: the suites table and its paragraph describe how the integration suite gets its server. It starts a container unless SURVSYS_SQLSERVER names one.   6. The whole integration suite run in a container. Failures caused by the container (sign-in, timing, collation) are fixed here.
