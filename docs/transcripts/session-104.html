Work Plan

Turn a reportable eICR into a case. Survsys.Data gets two tables in one migration, EcrCases: ecr_case_link (an eICR version, the case it was written to, when; unique on the pair) and ecr_case_value, owned by a link (the table written, the row id, a key -- the field name for a value on a row the eICR did not create, the row's natural key for a row it did -- and the value as written, as text), so each value records the eICR id and version it came from through its link; ecr_document gains a case status ('linked' or 'review', null until decided) and the reason for a review. A static EcrCaseWriter in Survsys.Api takes an eICR once it and an RR with a reportable condition (RRVS1, mapped to a catalogue condition, as EcrReportability routes it) are both on file -- EcrIntakeService calls it after storing either -- and for each reportable condition: a later version of a set already linked goes to the case its earlier version was written to; otherwise the patient is matched by phase 9's matcher (PersonMatchQueries): one exact candidate and no probable one is that person, no candidate at all is a new person made from the eICR's demographics, and anything else sets the document to review with why. On the person, the open case on that condition -- including one opened from ELR -- is linked, or a new case opened. A reviewer settles a review through POST /api/ecr-documents/{id}/case naming the person (or none, for a new person) and optionally the case, behind the privilege staged-message promotion uses, and GET /api/ecr-documents/{id}/person-matches lists the candidates; the document detail carries its case status, reason and linked cases. The writer then writes the eICR onto the case: for a person it created, the demographics; the patient's address as ELR adds one, its county stored as the county or the county equivalent as the CountyPrograms ecr setting names, the other filled from the town by AddressRules.FillConnecticutCounties; the encounter as an Encounter; each problem as a case note of type eCR, and the earliest trigger problem's onset as the disease onset date; each medication as a PersonTreatment (the treatment found by name, added to the catalogue where none is); pregnancy as the case's pregnant answer; each travel entry as an Exposure; the first occupation as the case's occupation; and, only where the eICR's custodian is listed in the new EcrIntakeOptions.LabSenders, its results as a lab. A later version updates each value and row its earlier version wrote whose current value still equals what was written, adds rows with new keys, removes unedited rows its predecessor wrote that it no longer carries, and leaves alone everything a user has changed and every value it did not write; a lab is added once by its key and never updated. Integration tests against SQL Server prove a new case, a link to an ELR-opened case, and a second version.

Ecr case values

EcrCaseWriter writes the eICR onto each linked case, recording an EcrCaseValue for every value and row it writes: a new person's demographics; the address, its county by the CountyPrograms ecr setting and the other from the town; the encounter; problems as eCR notes and the earliest trigger onset as the disease onset date; medications as treatments; pregnancy as the pregnant answer (Yes, or No where negated); travel as exposures; the first occupation; and the results as a lab only where the custodian is in the new EcrIntakeOptions.LabSenders (empty in appsettings.json). A later version updates what its predecessor wrote where the current value still equals the written text, adds rows with new keys, removes unedited rows it no longer carries, and leaves anything edited or not its own; a lab is added once by key. The pure parts -- the written text of a value and whether it was edited -- are public and unit-tested in EcrCaseWriterTests.
