Session 97: Classification shown on save, and on encounter saves

*Inserted after session 96. Session 96 left two things owed. Its step 3 asked for each rule's outcome to be shown to the user on save. The outcome is written as an administrative note, which the user finds only by opening the Notes tab. The Clinical, Laboratory, Investigation and Administrative tabs tell the report page nothing when they save, so the case status in its header stays as it was until the page is reloaded. And an encounter's save does not run the rules, though the influenza rule reads a facility encounter as the case's recorded hospitalization, so its finding stays stale until something else saves the case. Both come before the Phase 12 walkthroughs because "see a case classified on save" crosses them.*

*Non-goals: no hospitalization field and no "Out of State" agency. Both are decisions for session 108's gap analysis.*

  1. Register.
  2. Survsys.Api: every route that classifies a case answers with the classifier's outcome — the case status after it and that save's findings. The encounter add, edit and delete routes run the classifier too.
  3. Survsys.Api: when a case is classified again, a classification note whose finding no longer holds is struck, so a case does not gather findings that are no longer true. The note for a finding that still holds is still written once.
  4. Survsys.Web: each tab that saves a case tells the report page. The page re-reads the case's status and shows that save's findings beside the save. Every element id stays unchanged.
  5. Survsys.UnitTests and Survsys.IntegrationTests: the outcome each classifying route answers with, an encounter's save reclassifying an influenza case, and a stale classification note struck. These reach SQL Server.
  6. Survsys.E2ETests: a Playwright test that adds a positive lab to a case with no status and, without a reload, sees the header show Confirmed and the findings shown beside the save.
  7. Cross-provider verification.
  8. Full test suite, the integration suite included, recorded as the run of record.
  9. Close-out.

Work Plan

Show the user each save's classification without a reload, and run the classifier on encounter saves. In Survsys.Api the CaseClassifier keeps the outcome of the case it classified (the report id, the case status after it and that save's findings) on the request's SurvsysDbContext, and one small middleware answers every route with a Case-Classification response header carrying it as JSON (a CaseClassificationResponse contract), which reaches the 204 deletes as well as the bodies, so every classifying route answers with its outcome without changing any response shape. The encounter add, edit and delete routes call the classifier, so an influenza hospitalization case's finding follows its facility encounters. The classifier writes one administrative note per finding, marked by a fixed prefix, and strikes any unstruck classification note on the case whose finding no longer holds; a finding that still holds keeps its one note. In Survsys.Web a delegating handler on the Clinical, Investigation, Administrative, Labs and Encounters clients reads the header into a circuit-scoped CaseClassifications service; the report page listens to it and re-reads the case so the header's case status is current, and a small ClassificationFindings component beside each of those tabs' save shows that save's findings. No existing element id changes. Unit tests cover the header middleware, the handler and the service; integration tests cover the header each classifying route answers with, an encounter save reclassifying an influenza case, and a stale note struck; a Playwright test adds a positive lab to a case with no status and sees Confirmed in the header and the findings beside the save without a reload.
