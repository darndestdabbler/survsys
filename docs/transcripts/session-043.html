Work Plan

Session 043 gives the outbound CDC notification half its first structure: the notification guides a case is exported under, and the catalogue of CDC PHIN variables each guide carries. Survsys.Data gains five reference tables under the legacy NMI snake_case names, with one migration creating them -- phin_var (a CDC PHIN variable definition: its identifier, description, HL7 data type, priority, status, code system, and the bare ruleset ids a later session fills, holding the 588 CDC variables the legacy snapshot carries), guide (a notification guide by name), condition_detail (the guide assigned to a condition, one per condition), guide_phin_var (which PHIN variables a guide carries), and guide_link (the guides a guide pulls in alongside its own) -- each a bare entity with its internal IEntityTypeConfiguration and a DbSet, the association tables keyed by their natural pairs and every cross-table id left a bare int or string with no navigation, exactly as the existing reference entities do. Survsys.Messaging gains the PHIN variable mapping over that catalogue, built so it takes the guides, their variable memberships, their links and the variable definitions as plain in-memory data rather than reaching for a DbContext -- so the module keeps the fence the architecture test already asserts, referencing neither Survsys.Data nor Entity Framework Core. The mapper resolves, for a condition, the guide it is exported under and then the PHIN variables that guide carries together with the variables of the guides it links, returned distinct and ordered; a condition with no assigned guide resolves to no variables rather than throwing. Survsys.UnitTests gains PhinVariableMapperTests, the tests named after the mapper, covering a condition whose guide carries variables, a guide that pulls variables in through a link, the distinct-and-ordered union, and a condition with no guide.

Phin mapping

Survsys.Messaging: the PHIN variable mapping over the notification-guide catalogue, taking it as plain in-memory data rather than reaching for a DbContext, so the module keeps its fence against Survsys.Data and Entity Framework Core and references neither. PhinVariableCatalog.cs: the input records the mapper reads, each a small immutable record and none of them a Survsys.Data entity -- a PHIN variable definition (its identifier string, its description, its HL7 data type, its priority, its code system; the fields a caller carries over for a variable the mapping returns), a condition-to-guide assignment (the condition id and the guide id it is exported under), a guide-to-variable membership (the guide id and the PHIN variable identifier it carries), and a guide link (the guide id and the id of a guide it pulls in alongside) -- gathered in one PhinVariableCatalog container the caller fills from whatever source it has. PhinVariableMapper.cs: the mapper built over a PhinVariableCatalog, exposing a method that resolves the PHIN variables for a condition -- it finds the guide the condition is exported under, gathers that guide together with the guides it links, unions the variable memberships of those guides, resolves them to their definitions, and returns them distinct and ordered by the variable identifier. A condition with no assigned guide, or a guide that carries no variables, yields an empty result rather than throwing; a membership whose variable the catalogue does not define is skipped. Write no test in this step.

Phin mapping tests

Survsys.UnitTests/PhinVariableMapperTests.cs, the test file named after PhinVariableMapper.cs. Build a small in-memory PhinVariableCatalog and assert the mapper's behaviour: a condition whose guide carries variables resolves to exactly those variables; a guide that links another guide resolves to the union of both guides' variables; the result is distinct (a variable carried by both a guide and its linked guide appears once) and ordered by the variable identifier; a condition that has no assigned guide resolves to no variables rather than throwing; and a guide membership naming a variable the catalogue does not define is skipped rather than throwing. Change no production code in this step.
