Work Plan

Validate every eCR document as it is taken in and give reviewers a screen to read it. The HL7 artifacts are vendored unchanged under Survsys.Messaging/Cda: the CDA R2 schema with the SDTC extensions (HL7/CDA-core-2.0), the four IG schematrons with the vocabulary files they read (eICR R1.1, R3.1, R3.1.1, RR 1.1), the ISO Schematron XSLT 1.0 skeleton (schematron/schematron), and the HL7 CDA stylesheet (HL7/CDA-core-xsl). The schematrons declare queryBinding xslt2 but use XPath 1.0 throughout except two matches() calls in R3.1.1, so a CdaValidator in Survsys.Messaging compiles each schematron once through the skeleton with XslCompiledTransform (the query binding read as xslt1, matches() bound to a .NET regex extension function), and validates a document against the schema and the schematron for its kind and version, answering findings: source (schema or schematron), severity (the schematron rule's role -- fatal, error, warning -- and error for a schema violation), message and location. R3.1's 58 MB vocabulary file is not vendored: every value set R3.1's schematron looks up is in the R3.1.1 vocabulary, which is read in its place. Survsys.Data gets an ecr_validation_finding table owned by ecr_document, with its migration; EcrIntakeService validates each document it stores and stores the findings with it, never refusing a document for them. CdaStylesheet in Survsys.Messaging renders a document to HTML through the HL7 CDA stylesheet with JavaScript off. Survsys.Api adds GET /api/ecr-documents (the eCR queue: paged, filtered by feed, newest first, each row with its kind, feed, document id, version, received time and counts of errors and warnings) and GET /api/ecr-documents/{id} (the eICR rendered, the conditions, determinations and responsible agencies of its paired RRs -- or for an RR, its own and its eICR's rendering -- and the validation findings of each document, marked with the document they belong to), behind the case-viewing privilege the staged-message queue uses. Survsys.Web adds an EcrClient, an eCR queue page and a document page that shows the rendered eICR in a sandboxed iframe beside the RR's conditions and the findings, with a nav entry. Unit tests validate a valid and an invalid document of each version (the IG sample, and the sample with its required ClinicalDocument/id removed).

Ecr endpoints

Add EcrEndpoints to Survsys.Api and its wire shapes to Survsys.Contracts, following MessageQueueEndpoints: GET /api/ecr-documents is the eCR queue, paged with the existing Paging, filtered by an optional feed, newest first, each row an EcrDocumentResponse (id, kind, feed, document id, version number, source, received at, error count counting fatal and error findings, warning count). GET /api/ecr-documents/{id} answers an EcrDocumentDetailResponse: the summary; the eICR's HTML from CdaStylesheet (the document's own for an eICR, its paired eICR's for an RR, null where the eICR has not arrived); the conditions of the paired RRs (for an RR, its own) read with CdaParser, each an EcrConditionResponse with its condition, determination, location, responsible agency and reporting timeframe; and the findings of the eICR and those RRs as EcrValidationFindingResponse, each naming the document kind and id it belongs to. Both require the case-viewing privilege; an unknown id is 404.
