Work Plan

Make a message's laboratory data land on the case, atomically, and let a message update a case the person already has. Survsys.Api gains MessageCaseWriter, a static class over SurvsysDbContext whose Open opens a case for a message -- through PersonConditionQueries.Add, as today -- and, in the same database transaction, writes the message's specimen (collection date, accession, specimen source by its specimen_source code, lab facility by the sending facility's name where one is on file), one test per result (LOINC as the master LOINC else the observation code, test status by the OBX-11 code on the test_status list, reference range, observed date) with its result (organism, value, coded result or interpretation, units), and a result whose observation names a resist_test_agent as a susceptibility with its resist_test_result; adds the message's address to the person where no address of theirs has that street and zip; and moves the message to assigned with that case by a conditional update that only moves a message still in a promotable state, so a failure anywhere rolls back the case, the labs and the assignment together, and a second promotion of the same message finds nothing to move and is refused with nothing written. LabQueries.Add joins a transaction already open instead of beginning its own. Both the promotion endpoint and MessageProcessingService.Assign open cases through it. Then the update: MessageCaseWriter.Update takes a message and one person and, when the message's case-management decision allows an update, chooses among that person's open, undeleted cases on the message's condition by a whitelist rule -- a structured rule, not the legacy free text, configured as MessageProcessing:Whitelist with per-condition overrides by condition code (exception, newest, never-new, always-new, time since onset in days, before/after the event date in days; with ignore-case-status), defaulting to a time-since-onset window -- with the legacy post-evaluation pruning of Not a Case cases when others match; an exception rule, a case with no reference date to test, or several matched cases sends the message to pending with why; no matched case opens a new one when the decision allows a new case, and a single match that is Not a Case (unless the rule ignores case status) opens a new one beside it. On a single matched case, the pure LabComparison compares the message's labs with the case's: no specimen with the same accession and collection date (and no other lab's same date, LOINC, result and organism) is ADD, writing the specimen onto the case; the same specimen with every incoming test already there with the same result is DUPLICATE (or UPDATE when the incoming test status ranks above the stored one by the test_status list's sort order, which upgrades it); the same specimen with tests it does not yet hold is UPDATE that knits those tests and their results onto it; and the same specimen and LOINC with a different result is EXCEPTION, which sends the message to pending. Before writing, the message's patient is scored against the case's person with the existing PersonMatchQueries, and anything but an exact match sends the message to pending as a person mismatch. Duplicate still assigns the message to the case and adds the person data. Decide sends an exact match with an open case on the condition to update rather than to pending, and PromoteMessageRequest gains an optional PersonConditionId, so a reviewer may promote a message onto a named existing case through the same Update with that case as the only candidate. Integration tests cover each comparison outcome and a promotion that fails part-way.
