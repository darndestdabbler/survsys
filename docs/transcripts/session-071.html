Work Plan

Find duplicate persons with the session-70 matcher and merge them. Survsys.Data's Person gains MergedIntoPersonId and MergedAt, the merged-away record's tombstone (a self-referencing foreign key, restrict on delete), added by a PersonMerges migration that also grants a new merge_persons privilege (Privileges.MergePersons) to the Administrator role; PrivilegeRules requires it for everything under /api/person-merges. Survsys.Api adds PersonMergeEndpoints: GET /api/person-merges/candidates returns candidate duplicate pairs among live persons (blocked on a shared last name, birth date or identifier value, scored and classified by PersonMatchRules with the configured PersonMatchThresholds, Probable or Exact only, best first, capped); POST /api/person-merges takes a PersonMergeRequest (the person kept and the person merged away) and, in one transaction, moves the merged person's cases (their vaccines, treatments and everything else travel with the case), labs, contact and exposure-source links, parent/guardian links, identifiers, aliases, name history, races, telephones, emails and addresses onto the kept person (composite-keyed aliases and races re-inserted only where the kept person lacks them, and the merged person's current address closed as of the merge when the kept person already has one), then marks the merged person a tombstone; the AuditInterceptor audits every one of those row changes inside the same transaction, so a failure leaves nothing changed and no audit. Person search and match candidates exclude tombstones. Survsys.Web adds a duplicates screen listing the pairs and a side-by-side merge screen comparing the two records, choosing which to keep and merging, both shown and linked only to a user holding MergePersons. Unit tests cover the privilege rule, request validation, pairing and the client calls; integration tests check every moved row after a merge and that a merge made to fail partway leaves both persons and their rows unchanged.
