Session 83: Reference data administration — code lists and addresses

*Inserted after session 81. Reference data must be viewable on an administration screen and kept current by an administrator, by editing a row or uploading a file, rather than by a release. Today only the five vocabulary tables can be uploaded or downloaded (/vocabulary, by VocabularyCsv). The code lists can be edited on /codes but not uploaded. ct_towns and zip_codes have no endpoint and no screen at all, and AddressRules reads the town seed in code, so a corrected row could not take effect. Zip codes reach an agency only by typing them into its form. The operator has decided the shipped rows need not be current or checked against an official list, such as the Census Bureau's, so long as an administrator can correct them. CtTownSeed stays as the starting data.*

*Session 81 also owes two things this session covers. The County and planning region columns on the person screen and the case search show a raw code such as 09003 rather than its name. And the end-to-end tests were not run, so its screens were never seen rendered.*

  1. Register.
  2. Survsys.Api: one CSV import and export for reference tables, built from what VocabularyCsv does. Export writes every row with a header row. Import first returns a preview of the rows it would add, the rows it would change, and the rows it refuses with each one's reason. Nothing is written until the administrator confirms. A row is matched to an existing one by the table's natural key, and an existing row the file leaves out is kept as it is. The vocabulary tables move onto it with their CSV columns unchanged.
  3. Survsys.Api and Survsys.Web: import and export for each code list on /codes, with the county list's state, FIPS code and kind, and with test types' conditions. A code is still retired by clearing Active, never deleted.
  4. Survsys.Api and Survsys.Web: endpoints and an administration screen for the Connecticut towns (town, county, planning region) and for the zip-to-county table, each with view, add, edit, import and export. AddressRules and ELR intake read the towns from the database, so an upload takes effect on the next save. Import and export of an agency's jurisdiction zip codes on /agencies. Each screen and action requires the administration privilege that /codes requires.
  5. Survsys.Web: the person screen and the case search show a county's and a county equivalent's name from the county list, not its code. Every element id stays unchanged.
  6. Survsys.UnitTests and Survsys.IntegrationTests: a preview that adds, changes and refuses rows; a confirmed import; an export read back in unchanged; a town corrected by upload and then used by the next address save. These reach SQL Server.
  7. Survsys.E2ETests: a Playwright test that uploads a CT town file and saves a Connecticut address with its town alone, then finds its county and planning region filled in by name on the Demographics tab, the person screen and the case search.
  8. Cross-provider verification.
  9. Full test suite, the integration and end-to-end suites included, recorded as the run of record.
  10. Close-out.
